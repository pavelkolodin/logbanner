# logdigger

`logdigger` — консольное приложение для Linux (Debian), написанное на Rust. Оно:

* разбирает сырой лог nginx и извлекает из каждой строки HTTP-`path` (вместе с query-string);
* собирает уникальные `path` в готовую структуру данных `std::collections::HashSet` — каждый путь сохраняется ровно один раз;
* ведёт файл «базы данных» известных путей и выражений вида «шаблон со звёздочкой»: три колонки `<expression> <path> <status>`;
* минимизирует базу, сворачивая избыточные записи;
* дополняет базу строками `NULL "<path>" BAD` для путей, под которые не подошло ни одно известное выражение.

Приложение **не придумывает выражения самостоятельно**: всё, что стоит в поле `<expression>`, задаётся извне (вручную) и воспринимается как данность. Настоящий движок regular expressions не используется — только собственный простой движок: wildcard `*` и экранирование через backslash (`\*` = литеральный `*`, `\\` = литеральный `\`).

## 1. Сборка приложения

### Требования

* Linux (проверено на Debian x86_64);
* Rust toolchain с `cargo` и `rustc` (сборка проверена на Rust 1.100, edition 2021).

Установка toolchain через rustup, если его ещё нет:

```bash
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y
source "$HOME/.cargo/env"
```

На Debian можно и системными пакетами (`apt install cargo rustc`), но версия компилятора в репозитории обычно старее.

### Сборка

```bash
cd logdigger
cargo build --release
```

Готовый бинарный файл: `target/release/logdigger`.

### Запуск тестов

```bash
cargo test
```

Тесты покрывают: движок сопоставления со звёздочкой, парсер строк базы, минимизацию базы, извлечение `path` из лога и полный цикл работы бинарника (включая идемпотентность повторного запуска).

### Зависимости

| Пакет (`crates.io`) | Назначение |
|---|---|
| `clap` (feature `derive`) | готовый разбор аргументов командной строки |
| `anyhow` | обработка ошибок и сообщения о них |

Используемые готовые структуры данных: `std::collections::HashSet<String>` (уникальные пути) и `Vec<DbRow>` (упорядоченный список строк базы). Движок `*`-выражений написан с нуля (`src/matcher.rs`), пакет `regex` намеренно не подключается.

## 2. Описание commandline-параметров запуска

```
logdigger --db <filename> [--in <filename>]
```

| Параметр | Обязательный | Описание |
|---|---|---|
| `--in <filename>` | нет | Входной файл с сырыми логами nginx (стандартный формат combined, как в `example.txt`). Если параметр не передан, разбор лога не выполняется: приложение только читает базу, минимизирует её и перезаписывает файл при изменениях. |
| `--db <filename>` | да | Файл «базы данных» — списка выражений и путей. Читается при старте и перезаписывается в конце работы, только если база изменилась. Если файла ещё нет — приложение стартует с пустой базой и печатает предупреждение. |

Также поддерживаются стандартные `-h/--help` и `-V/--version`.

### Формат файла `--db`

Каждая строка файла — три колонки, разделённые пробелом:

```
<expression> "<path>" <status>
== "<path>" <status>
NULL "<path>" <status>
```

* первая колонка — `<expression>`, либо зарезервированное значение `NULL`, либо зарезервированный маркер `==`;
* `==` — **expression копируется из `<path>`**: в памяти строка становится такой, «как если бы содержимое `<path>` стояло в первой колонке». Логически это срабатывание `<path>` на самого себя. При перезаписи файла маркер `==` **остаётся в первой колонке** — он не превращается в отдельную сущность в `--db`;
* строки с `<expression> == <path>` схлопываются **только при одинаковом `<path>`** (см. алгоритм, шаг 2): более широкое выражение такое совпадение не убирает;
* для строк с `<expression> == <path>` движок `<expression>` **отключён намертво** — срабатывает только точное равенство строк. Это защита от случайного `*` в самом пути: бредовый запрос `/\*/\*/\*\*\*\*sobaka\*/\*` после копирования в expression никогда не превратится в широкий шаблон и не будет ловить широкий спектр строк;
* `<expression>` отделён пробелом от `<path>`;
* `<path>` — HTTP-путь в двойных кавычках, например `"/index.php"`;
* `<status>` — **3-я колонка**: любое строковое значение, обычно `BAD` или `GOOD`; если встречается другое значение — оно сохраняется как есть (например `NEEDS-REVIEW`);
* если 3-я колонка в строке отсутствует — при чтении она приравнивается к `BAD`, и файл перезаписывается уже с колонкой (одна такая подстановка считается изменением базы);
* новые `NULL`-записи, добавляемые при обработке лога, сразу получают статус `BAD`;
* статус — метаданные: алгоритм сопоставления и минимизации его **не использует**, значение сохраняется как есть при любых операциях с базой;
* `<expression>` по умолчанию всегда `NULL` — означает «мы пока не знаем, каким выражением ловить этот путь»;
* `<expression>` может состоять из любых символов пути и символа `*` (asterisk) в любом месте;
* `*` означает «любое число любых символов, минимум ноль любых символов»;
* `\` (backslash) в `<expression>` — escape-символ: **любой символ после него воспринимается как одиночный литеральный символ для сравнения**:
  * `\*` = литеральный `*` (сравнивается как обычный символ, а не как wildcard);
  * `\\` = литеральный `\`;
  * `\a` = литеральный `a` (для неспециальных символов экранирование просто «отпускает» их);
  * одиночный `\` в конце выражения = литеральный `\`;
  * экранирование действует **только в `<expression>`**; сам `<path>` сравнивается как есть, обратные слэши в нём никак не обрабатываются;
* значение `<status>` не должно содержать двойных кавычек (иначе ломается разбор строки);
* пустые строки и строки, начинающиеся с `#`, игнорируются; неразобранные строки пропускаются с предупреждением в stderr;
* поле `<expression>` можно писать и в кавычках: `"/*.php" "/index.php"` — эквивалент `/*.php "/index.php"`.

Пример файла (`example.db`):

```
NULL "/robots.txt" BAD
/*.env "/.env" GOOD
*/wp-includes/wlwmanifest.xml "/2018/wp-includes/wlwmanifest.xml" GOOD
/*.php "/phpinfo.php" GOOD
== "/test" BAD
```

Между запусками файл можно править руками: любой `NULL`, любое выражение, маркер `==` и любой статус (`BAD`, `GOOD` или своё значение) можно поменять вручную — приложение при следующем запуске воспримет это как данность.

### Примеры запуска

```bash
# разобрать лог и обновить базу
./logdigger --in example.txt --db example.db

# только перечитать и минимизировать базу (без лога)
./logdigger --db example.db

# справка
./logdigger --help
```

Пример вывода:

```
db: 5 row(s) loaded, 0 collapsed, 0 malformed line(s) skipped
log: 73 line(s), 73 with request, 57 unique path(s)
log: 29 path(s) matched by expressions, 1 already in db, 27 new NULL row(s)
db: rewritten, 32 row(s) total
```

### Коды завершения

| Код | Значение |
|---|---|
| `0` | успех |
| `1` | ошибка чтения/записи файла (нет файла, нет прав и т.п.) |
| `2` | ошибка аргументов командной строки (например, не передан `--db`) |

## 3. Описание алгоритма работы

### Шаг 1. Чтение и парсинг `--db` при старте

1. Файл `--db` читается целиком; отсутствие файла — это пустая база (с предупреждением).
2. Каждая строка парсится в тройку `(expression, path, status)` — три колонки, разделённые пробелом:
   * `<path>` берётся из последней пары двойных кавычек строки;
   * всё, что стоит перед этой парой, — поле `<expression>`; если оно равно зарезервированному маркеру `==`, то в памяти в поле expression **копируется содержимое `<path>`** — «как если бы оно стояло в первой колонке»; внешние кавычки выражения, если есть, снимаются; пустое поле трактуется как `NULL`, регистр `NULL` не важен;
   * всё, что стоит после пары кавычек, — 3-я колонка `<status>`; если её нет, значение подставляется `BAD` (и факт подстановки запоминается: такая строка станет поводом для перезаписи файла, чтобы колонка появилась на диске);
   * пустые строки и комментарии `#` пропускаются; не разобранные строки пропускаются с предупреждением.
3. Строка помнит, что была прочитана через маркер `==`: правила сопоставления и минимизации у неё **те же**, что и у строки, где expression записан буквально равным пути, а при перезаписи файла маркер возвращается в первую колонку — новых сущностей в `--db` не появляется. Для **всех** строк с `<expression> == <path>` при сопоставлении движок `<expression>` **отключён намертво**: срабатывает только точное строковое равенство. Даже если в пути случайно оказался `*` (например, бредовый запрос `/\*/\*/\*\*\*\*sobaka\*/\*`), такая строка ловит только саму себя и никогда — широкий спектр строк.
4. Результат — упорядоченный список записей `Vec<DbRow>` (порядок строк файла сохраняется).

### Шаг 2. Минимизация базы (схлопывание записей)

Цель: минимизировать число строк `--db`, чтобы **каждое выражение существовало только один раз**, а устаревшие `NULL`-записи, уже покрытые известными выражениями, исчезли. Формат сопоставления — «подходит ли `<path>` под `<expression>`» (см. алгоритм ниже).

Алгоритм двухфазный, выполняется сразу при загрузке:

**Фаза A — отбор строк с выражениями (обход сверху вниз):**

* строка с `NULL` в фазе A не участвует;
* строка с выражением `E` **отбирается**, если:
  * такого же `E` ещё не отобралось (точное совпадение поля `<expression>`), и
  * пример `<path>` этой строки не покрыт ни одним уже отобранным выражением;
* иначе строка отбрасывается: это дубликат выражения, либо её пример уже ловится другим выражением;
* **особый случай — «срабатывание на самого себя»**: если у строки `<expression> == <path>` (в том числе прочитанной через маркер `==`), покрытие более широким выражением её **не удаляет** — такая строка схлопывается только когда её `<path>` совпадает с `<path>` уже отобранной строки (точный дубликат выражения либо более широкое выражение с тем же путём-примером). Более широкое выражение с другим путём примера её не убирает.

**Фаза B — сборка итогового списка:**

* отобранные на фазе A выражения остаются в базе **всегда** — выражение не может быть удалено собственной сработкой (иначе база опустела бы, ведь выражение обычно совпадает со своим примером);
* каждая оставшаяся `NULL`-строка проверяется против **всех** отобранных выражений:
  * если какое-либо выражение подходит к её `<path>` — строка удаляется (путь уже накрыт, `NULL` устарел);
  * если такой `<path>` уже встречался у другой `NULL`-строки — дубликат удаляется;
  * иначе строка остаётся в базе.

У выживших строк 3-я колонка `<status>` сохраняется как есть (`GOOD`, `BAD`, чужое значение — неважно); минимизация на статус не влияет и сама статусом не управляет.

Количество удалённых строк фиксируется: если оно больше нуля, база считается изменённой.

Пример схлопывания:

```
было                                       стало
NULL "/index.php" BAD                      /*.php "/old.php" GOOD
/*.php "/old.php" GOOD           →
NULL "/robots.txt" BAD                     NULL "/robots.txt" BAD   (не покрыт — остаётся)
```

> Схлопывание использует то же правило сопоставления, что и обработка лога (шаг 5), поэтому результат детерминирован и идемпотентен: повторный запуск над уже минимизированной базой ничего не меняет.

### Шаг 3. Разбор `--in` и извлечение уникальных `path`

1. Если аргумент `--in` передан — файл читается построчно (`BufReader`).
2. Из каждой строки берётся request-блок — первая пара двойных кавычек, например
   `"GET /index.php?option=com_jce&task=cpanel.feed HTTP/1.1"`.
3. Из request-блока берётся второй токен — HTTP-`path` вместе с query-string, то есть `/index.php?option=com_jce&task=cpanel.feed`.
4. Абсолютный URI (`http://host/path`) нормализуется к `/path`; `OPTIONS *` и строки без request-блока отбрасываются.
5. Все извлечённые `path` складываются в `HashSet<String>` — каждое значение хранится **только один раз**, дубликаты строк лога отсекаются на этом уровне.

### Шаг 4. Движок `<expression>` (сопоставление со звёздочкой)

Реализован с нуля в `src/matcher.rs`; настоящий движок regex не используется.

Движок применяется **только к строкам, где `<expression> != <path>`**. Строки-самосопоставления (прочитанные через `==` либо записанные буквально с одинаковым expression и path) движком не проходят — для них работает точное равенство строк (см. шаг 1): в `<path>` может случайно оказаться `*`, и такой путь обязан ловить только сам себя.

Семантика:

* `*` (не экранированный) = wildcard: «любое число любых символов, минимум ноль»;
* `\X` в выражении = **одиночный литеральный символ `X`** для сравнения:
  * `\*` — литеральный `*` (не wildcard);
  * `\\` — литеральный `\`;
  * одиночный `\` в конце выражения — литеральный `\`;
* все прочие символы — точные; литеральный `*` в `path` не отождествляется с wildcard в `expression`.

**Компиляция.** Перед сравнением выражение разбивается в последовательность токенов `Literal(char) | Any`:

1. `\` + любой следующий символ → один токен `Literal(следующий символ)` (если `\` последний — `Literal('\')`);
2. неэкранированный `*` → токен `Any`;
3. любой другой символ → `Literal(себя)`.

**Сопоставление** — классический жадный обход двумя указателями (`pi` по токенам `pattern`, `ti` по `text`) с откатом к последней встреченной wildcard:

1. токены `pattern` и символы `text` сравниваются попарно: `Literal(c)` требует точного равенства, при совпадении оба указателя идут вперёд;
2. если очередной токен `Any` — запоминаем его позицию и позицию в `text`, отпускаем wildcard вперёд (пробуем съесть 0 символов);
3. при несовпадении `Literal` — если `Any` уже встречался, возвращаемся к нему и даём ему съесть ровно один дополнительный символ `text`, затем продолжаем сравнение;
4. если `Any` не было — возврата нет, совпадения не будет;
5. когда `text` закончился, остаток `pattern` должен состоять только из `Any` (они означают пустую строку); иначе совпадения нет.

Сложность: время `O(len(pattern) × len(text))` в худшем случае, память `O(1)` по указателям; реализация сравнивает `char`, поэтому корректно работает и с не-ASCII путями.

Проверки поведения:

| `expression` | `path` | результат | пояснение |
|---|---|---|---|
| `/index.php` | `/index.php.test` | **нет** | без `*` сравнение точное |
| `/index.php*` | `/index.php.test` | да | `*` в конце = любой суффикс |
| `/*.env` | `/api/.env` | да | `*` в середине |
| `*wp-includes/wlwmanifest.xml` | `/blog/wp-includes/…` | да | `*` в начале |
| `*.php` | `/index.php?x=1` | **нет** | путь не заканчивается на `.php` |
| `/index.php` | `/index.php` | да | точное совпадение |
| `\*` | `*` | да | литеральный `*` (пример из задания: `\*` = `*`) |
| `\*` | `/index` | **нет** | одиночный символ `*` ≠ `/index` |
| `/a\*b` | `/a*b` | да | литеральный `*` внутри пути |
| `/a\*b` | `/axb` | **нет** | `*` не замещает `x` — это литерал |
| `\\` | `\` | да | литеральный `\` (пример из задания: `\\` = `\`) |
| `\\*` | `\upload` | да | литеральный `\` + wildcard `*` |
| `*\*` | `/foo*` | да | wildcard + литеральный `*` в конце |

### Шаг 5. Проверка уникальных `path` по базе и добавление новых записей

Для каждого уникального `path` из шага 3 (обход в отсортированном порядке — для детерминированного результата):

1. `path` прогоняется через **все** известные выражения из базы (строки, где `<expression> != NULL`); для строк с `<expression> == <path>` вместо движка проверяется только точное равенство строк (см. шаг 1);
2. если есть **хотя бы одна** сработка — путь отбрасывается, в базу ничего не добавляется;
3. если сработок нет:
   * если такой `<path>` уже присутствует в базе (это пример какого-то выражения или уже существующая `NULL`-запись) — ничего не добавляется (дубликат не нужен);
   * иначе в конец базы добавляется новая строка `NULL "<path>" BAD` — «мы пока не знаем, каким выражением ловить этот путь», статус новой записи — `BAD`.

Важно: приложение **не генерирует выражения** — оно может только констатировать, что путь уже накрыт заданным извне выражением или что путь неизвестен (`NULL`).

### Шаг 6. Перезапись файла `--db`

Файл `--db` перезаписывается целиком (в порядке строк базы, путь всегда в двойных кавычках, статус — третьей колонкой, маркер `==` остаётся в первой колонке, если так стоял), если есть хотя бы одно из изменений:

* при загрузке/минимизации (шаг 2) схлопнулись строки;
* в каких-то строках отсутствовала 3-я колонка и она была подставлена как `BAD`;
* при обработке лога (шаг 5) добавились новые `NULL`-записи.

При перезаписи строки **группируются** (стабильная сортировка — относительный порядок внутри группы сохраняется):

1. сначала строки, в `<expression>` которых есть `*` (в том числе экранированный `\*`);
2. затем прочие строки с реальным `<expression>`;
3. затем строки с маркером `==` в первой колонке (выключенные expressions);
4. последними — **все** строки с `NULL` в первой колонке.

Если изменений не было — файл не трогается вовсе.

Повторный запуск с теми же входными данными не приводит ни к каким изменениям (идемпотентность), что делает запуски `logdigger` безопасными для регулярного применения к растущим логам.

### Сводка потока данных

```
--db file ──▶ парсинг строк (3 колонки; нет статуса → BAD) ──▶ минимизация (A+B) ──▶ Vec<DbRow>
                                                                          │
--in file ──▶ парсинг строк ──▶ HashSet<unique paths> ──▶ проверка по всем выражениям
                                                                          │
                       ┌─────────────────────────────────────────────────┘
                       ▼
        сработали ──▶ отбросить        не подошло ──▶ добавить "NULL <path> BAD"
                       │                                        │
                       └──────────────┬─────────────────────────┘
                                      ▼
     изменения? (схлопывание / подставленный BAD / новые записи)
              да ──▶ перезаписать --db        нет ──▶ файл не трогается
```
